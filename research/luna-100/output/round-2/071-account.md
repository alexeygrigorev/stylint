# My Portfolio Project Selection Process

When I prepare plans for AI Shipping Labs members, people often ask what they should build for a portfolio. There are many possible answers, so choosing one can be difficult. I start with a domain and work backwards from the problems companies in that domain are solving.

An active portfolio on GitHub can help hiring managers understand your work. It can also lead to collaborations, freelance conversations, and other opportunities. A personal utility shows that you notice problems, although one private tool may say little about the role you want.

Take-home assignments, hackathon contributions, community projects, and open-source work can also become portfolio pieces when you explain where they came from.

For a role-targeted project, I don't start with a fashionable framework. I choose a domain and list five to ten companies that hire for the role. Current job openings are useful. Engineering blogs, case studies, and product pages show what teams build and what problems return across the domain.

I collect job descriptions and engineering material separately. Job descriptions show responsibilities, team context, and required skills, while engineering posts show what teams built and the problems they had to solve in practice.

I use technology names as clues, then extract the problem behind them. A post about an AI conversation partner might reveal issues with dialogue quality and learner feedback. Grounding, evaluation, and latency can also be problems. These become project directions, while the framework named in the post is a later decision.

Next, I group problems that appear across several companies. A problem from one job description may be tied to a temporary situation or one team's specific product. A shared theme gives me a project that makes sense in more than one interview.

From that list, I create several candidates. For each one, I describe the user, input, and output. I also record why it fits the domain.

Only then do I choose technologies. I ask which tools the target companies use and map each proposed technology to a source. The final stack is still my decision. I don't try to learn every tool in the research because a project becomes hard to finish when it contains too many new things.

Evaluation and monitoring belong in the plan from the beginning. A system that generates an answer without checking whether it's correct is incomplete. I want an evaluation harness, logs or monitoring, tests for important behavior, and a README that a hiring manager can scan quickly.

In the README, I explain what the project does and who uses it. I also explain what goes in, what comes out, how it's evaluated, and why the stack fits. The code matters too, but hiring managers often decide from the README whether a project deserves a closer look. A project that runs end to end on real input is stronger than a repository that's technically elaborate but never used.

One project can lead to another. I can stay in the same domain while varying the model provider or technical approach. Over time, the portfolio shows a range of skills and a reason for the choices. That's easier to discuss than a collection of unrelated demos.
