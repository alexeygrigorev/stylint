# Choosing a Portfolio Project from Evidence

A portfolio project is easier to choose when it starts with a direction. Pick a domain, study companies working in it, and identify problems shared by several teams. A project with that evidence is easier to explain in an interview.

## Start with a domain

Choose a domain where you might want to work. This is more focused than applying to every job and choosing a project at random. It's also more durable than targeting one company. A vacancy can close before the project is finished, and one company's problem may not transfer to other interviews. A shared problem across several companies can give one project a wider use.

## Find companies and sources

List five to ten companies that hire for the role or work on relevant problems. Current and past openings are useful. Engineering blogs, case studies, product pages, and other public technical material can show what teams build.

Use job descriptions and engineering blogs for different reasons. Job descriptions describe responsibilities, team context, and skills, while engineering posts explain systems that teams built and the problems they encountered. Keep the two kinds of material separate during research so the evidence stays clear.

Technology names are clues, not project ideas. A post about an AI conversation partner may reveal dialogue quality and learner feedback problems. Grounding, evaluation, and latency can also be issues. Those problems can become project directions. The framework named in the post is a later implementation choice.

## Extract and group problems

Turn the source material into a list of problems before proposing solutions. For each one, record who has it, what input they have, and what outcome they need. Record where the evidence came from as well. Then group problems that appear across more than one company. A recurring theme is usually a stronger portfolio target than an isolated need.

Once a theme is clear, create about five project candidates. For each candidate, describe the project. Name its user, input, and output. Add the reason it fits the domain. This makes the options comparable before implementation begins.

## Choose the stack after the problem

Pick one candidate and map technologies to the companies or source documents that use them. This gives the project a domain-relevant stack to discuss in an interview. The agent can suggest options from the collected evidence, but the final decision remains yours. Keep the set small enough to build and use.

## Show that the project works

An AI project needs more than generated output. Add an evaluation harness, logging or monitoring, tests, and a README that a hiring manager can scan quickly. Explain what you built and who uses it in the README. Describe the input, output, evaluation, and reasons for the technology choices there as well.

Make the project usable end to end by feeding it real input and checking that useful output comes back. A working project gives you something concrete to discuss. It shows more than a technically elaborate repository that nobody has run.

After the first project, stay in the same domain and vary the model provider, retrieval method, or another implementation detail. A coherent set of projects can show range while preserving a reason for each choice.
