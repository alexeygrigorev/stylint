# The Projects I Stopped Building

I have a lot of repositories that began with a serious idea and ended with an empty commit history. That became more visible as coding agents made it cheap to try another idea. My personal GitHub account had 195 repositories when I wrote this, in addition to projects in the DataTalks.Club and AI Shipping Labs organizations.

The first project in this group was Code Explainer. I built it as a Streamlit application that accepted a GitHub URL, downloaded the main branch, and let an agent inspect directories, files, and search results. The interface showed which files the agent had looked at and the cost of a request. Follow-up questions could continue in the same context. It was a reasonable tool, but Claude Code made it unnecessary. A coding agent could clone a repository and answer the same questions directly, without me maintaining another interface.

The fitness tracker was more personal. I had tried existing workout applications and none matched the way I trained, so I asked Claude Code to build one. The first attempt used whatever frontend and backend choices the agent preferred. It did not work, and I did not understand why. I asked for a Django backend and a different frontend, then described the features I actually wanted: workout presets, warm-ups, drop sets, weights, repetitions, unfinished sessions, meals, sleep, and bodyweight. The list kept growing. Eventually the custom logic became too large and none of it worked properly. It was my first serious Claude Code project, so it still taught me how much guidance a real application required.

The metabolism simulator exposed a different problem. I wanted to see whether Claude could work for many hours through a continuation loop. The application was supposed to model food, exercise, glucose, hormones, energy, and recovery for my own routines. After three hours it had made an attractive interface, but the buttons did nothing. Later it displayed demo data instead of fixing a broken API. After several days there was a substantial application, but it was not reliable. That failure helped me understand why an agent needs requirements, tests, review, and somebody who accepts the work.

CodeHive and Litehive followed from that lesson. CodeHive tried to enforce a pipeline with a project manager, software engineer, QA engineer, and acceptance step, while also supporting several agent providers and several clients. It became too ambitious after I found that Termius already let me work from my phone. Litehive extracted the pipeline into a local command-line tool with SQLite state, worktrees, task recovery, and multiple agent engines. I spent more than a month on it, rewrote it repeatedly, and still could not make it stable.

Two smaller tools survived. Heru separated provider-specific command and session handling from Litehive. Quse normalized quota checks across Codex, Claude Code, Copilot, and Z.ai, and became the project I use most from that group. Merm also works as a pure Python Mermaid renderer, although I usually render diagrams in a browser with mermaid.js.

I do not consider these projects a waste. Some replaced a tool I no longer needed; others showed me why an approach was too rigid. The useful part can be a smaller project, a process, or simply a clearer understanding of what not to build next.
