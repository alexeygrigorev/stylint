# Building Personal Image Search Without a Heavy Stack

I take about 4,000 photos each year for courses, workshops, and repairs. I wrote
this synthetic style exercise with fictional collection sizes, project names,
timings, and hardware details. Last month I remembered a photo of a boiler
label, but I couldn't find it among screenshots and workshop pictures.

My first attempt used a commercial cloud photo library. It found people and
places well, but it was weak at boiler labels, whiteboard sketches, and course
slides. I also wanted the index on my own disk.

In this post, I'll share:

- what I indexed,
- how I generated captions and metadata,
- how I built the search index,
- what the interface does,
- what I gave up by keeping it small.

## The indexing scope

I started with 11,482 images in `photos/`, `screenshots/`, and `whiteboards/`.
The collection contained 6,000-pixel photographs, 240-pixel icons, and slide scans. I
excluded `downloads/` because it held duplicate memes and temporary assets that
had no lasting value.

I set a narrow goal. I wanted to find one image from a phrase such as "boiler
pressure label" and open its folder within 30 seconds. I didn't need automatic
sharing or a mobile application. The scope stayed small because I only wanted a
first useful index for my own photo and screenshot collection.

I wrote three requirements before choosing tools:

- run on the existing home server,
- keep captions and vectors next to the images,
- allow me to delete any generated caption,

and one more rule: nothing leaves the server after the initial captioning call.
I can redo captions with a local model later, but I wanted a useful index in one
weekend.

## Generate captions and metadata

Each record starts from a JSON file beside the image. The filename stays
unchanged, and the sidecar file uses the `.json` suffix.

The sidecar has these fields:

```json
{
  "image": "photos/boiler/IMG_4471.jpg",
  "caption": "A white boiler label showing a pressure gauge between 1.0 and 2.0 bar.",
  "captured_at": "2025-11-18T10:14:00+01:00",
  "folder": "boiler",
  "visibility": "private"
}
```

For metadata, I used ExifTool, a tool for reading and writing image metadata.
It supplied capture time, camera model, and GPS coordinates when present. I
stripped GPS values from images captured indoors, which removed 180 records from
the searchable set.

For captions, I sent the center 1,600 pixels of each image to a vision model
through its API. Small thumbnails and screenshots went through unchanged. I
added a folder-specific prompt: photographs got physical descriptions, and
whiteboards got text and diagram descriptions.

The process took 4 hours 20 minutes for 11,482 images and cost $7.84. I rate
limited it to 6 requests per second. About 312 captions were unusable because
the model described a visible error message instead of the interface around it.
I queued those for a second pass with a larger crop.

I also read the captions in samples of 100. Forty-two had hallucinated brand
names, so I removed manufacturer guesses from the prompt and reran 2,900 images.
The later sample had 6 uncertain brand mentions, all phrased as "appears to
read".

## Build the index

I chose SQLite (a small embedded relational database) for records and metadata,
plus SQLite vector extensions for embeddings. Each image gets a 384-dimensional
vector generated by a small open image-embedding model. I put caption text into
a full-text index and the vector beside it, so one query can use both.

The index schema uses three tables:

- `images`: path, capture date, folder, and file hash,
- `captions`: caption text, model, and created date,
- `vectors`: image ID and embedding blob.

The file hash prevents duplicates. On the first build, it found 1,204 duplicate
photos and 38 duplicate screenshots. I kept one copy in the index and left both
files on disk because I didn't want a search tool to delete anything.

The first indexing run took 22 minutes on the home server, an eight-core machine
with 32 GB of memory. The database occupies 3.1 GB, with captions and vectors
accounting for 2.2 GB. Startup takes 1.8 seconds, acceptable for a tool I open a
few times per week.

## Build a small interface

I built the interface with FastAPI (a Python framework for HTTP APIs) and one
page. I gave the page a text box, an optional folder filter, and a date range.
Each result appears as a 220-pixel square with 180 caption characters beneath
it.

I kept the query path to five steps:

```text
query -> embed query -> hybrid score -> filter -> top 40 results
```

For the hybrid score, I combine full-text rank and vector similarity. Full-text
search gets 60% of the score for quoted phrases, while vector similarity gets
60% for physical descriptions. If the user selects a folder, the filter runs
before scoring, so results don't waste space on the wrong collection.

A query for "boiler pressure label" returns the target photo first. It also
returns the instruction manual page, a close-up of the valve, and a screenshot
of a forum post. That third result is useful more often than I expected.

For "whiteboard retrieval evaluation", the best result is a photo from March.
The caption names "arrows from questions to metrics", which is how I remember
the sketch. Exact filename search would have failed because the image was named
`IMG_2844.jpg`.

## Limits of the small design

I traded convenience for control. There's no mobile application, face grouping,
or automatic album creation. I can use the index from my phone only through the
browser on my home network. Captions for handwritten notes are also uneven:
they work when the writing is clear, and they fail on hurried old notes.

Maintenance remains modest but real. After a camera import, I run the captioner
on new files and rebuild the full-text index. That takes 3 to 8 minutes for a
typical month. If I change the embedding model, I regenerate all 11,482 vectors.

I also keep a review habit. Every week, I mark the first 20 results for two
queries as useful or useless. They don't produce a formal benchmark, but they
have already suggested two prompt changes and one missing folder.

## Closing note

The sidecar file turned out to be the most useful part. The original image stays
untouched, the caption can be deleted, and I can rebuild the index without losing
human edits.
