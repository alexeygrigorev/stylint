# The Order I Review AI-Generated Code In

I wrote this synthetic style exercise as a how-to guide. LoanReview, its data and dates are fictional.

In June 2026, a coding agent changed 27 files in a fictional loan-review service. The diff added a FastAPI endpoint, a decision table, two database migrations and 38 tests. All tests passed, and the change still needed a careful review.

A green test suite tells me the code does what its tests describe. It doesn't tell me whether the tests describe the right behavior or whether the change fits the system. So I review in a fixed order.

In this post, I'll share:

- why the public interface comes first
- how I review stored state and failure behavior
- what I look for in generated tests
- how I handle naming and polish last
- the checklist I now use for large diffs

## 1. Check The Interface

Other code and other people rely on the interface first. In LoanReview, that means the route signature, response schema, database function names and command-line flags. I read those before reading implementation details.

For the June diff, the endpoint accepted a loan identifier and returned `decision`, `reason_codes`, `effective_date` and `review_id`. That was useful, but the schema also included an undocumented `internal_score`, which would have leaked a private value to the dashboard.

I ask three questions in my head and answer them from the diff:

- what input does the caller supply?
- what states can the response represent?
- what happens when the input is valid but the rule set has no answer?

The third case was missing. A loan could have a closed account and no active offer, so the endpoint needed a documented `MANUAL_REVIEW` response. That finding came from 10 minutes of interface reading, before I looked at a single SQL query.

## 2. Review State And Migrations

Next, I follow every field that survives after the request ends. Code from an agent can create a column without a plan for old rows, null values, updates or deletion.

The agent proposed `reason_codes` as a comma-separated string. It worked in the demo because every row had one reason. The business rules allowed four reasons, and the reporting team needed to count each one independently. I asked for a separate table instead.

The migration added that table and backfilled 18,400 rows.

I checked four things:

- the old column remains readable during deployment
- the backfill is idempotent
- new writes go to both places for one release
- a later migration can remove the old column

The agent produced all four on the second pass. The important change was my review comment: name the deployment window and the rollback command, rather than saying the schema should be normalized.

## 3. Follow Errors And Boundaries

After state, I read the failure paths because the happy path usually gets attention from the model. Partial failures, timeouts and retries are where an agent-generated change becomes expensive.

LoanReview called a credit-rules service with a two-second timeout, and the client generated by the agent retried immediately three times. Because that behavior could triple load during an outage, I asked for one retry after 250 milliseconds with an idempotency key.

I also asked for a circuit breaker after five failures.

I also checked the boundary between validation and authorization. The endpoint validated the loan identifier before confirming that the current user could see that loan. The authorization check existed, but it happened after a database lookup that returned some loan details in the error context.

I made the code validate the input, authorize the identifier, then load data. That order is now in the repository's review guide.

## 4. Read The Tests Against Behavior

I read agent-generated tests after the implementation because I want to see what the code claims about its interfaces. The tests are useful evidence only when they can fail.

The 38 new tests looked impressive. Fourteen tested private helpers, while only five covered the new endpoint. I asked the agent to keep eight helper tests and add endpoint tests for each response state.

The endpoint set then covered:

- valid approval with two reason codes
- manual review when no rule matches
- validation failure for a malformed identifier
- authorization failure with no loan data in the response
- timeout and single retry

One test mocked the wrong response object and still passed. That was my reminder to run a mutation check. I temporarily inverted one rule and confirmed that at least one test failed. Then I restored the code.

For the migration, the test applied the upgrade, inserted old-format and new-format rows, ran the backfill twice and asserted that the counts stayed stable.

## 5. Leave Naming For Last

Naming and formatting matter, but they're poor opening questions. If I start there, I can spend 40 minutes on `process_data` and miss a missing authorization check.

Once behavior looked right, I renamed `handle_loan_v3` to `review_loan`, moved 23 lines into a service function and deleted one compatibility parameter that had no caller. The agent then updated imports and tests in a separate commit.

This is also where I look for repeated setup, and four endpoint tests repeated the same seven-line fixture. I moved it into one helper and added a comment explaining the loan state. The diff became 190 lines smaller without changing behavior.

The final pass takes the least technical judgment. I run the formatter, check the README commands and read the commit message. If those need changes, they don't belong in the same commit as the behavioral fix.

## Closing Notes

The fixed order turns a large diff into smaller review tasks. I review the interface, state, failure paths, tests and then polish. I can stop after any layer and leave concrete comments.

For LoanReview, that order found a leaked field, a storage design problem, a retry risk and an authorization-order bug before release. The green checkmark caught none of them.
